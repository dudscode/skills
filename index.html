01

Estrutura de uma Skill

Anatomia completa

minha-skill/
├── SKILL.md ← obrigatório
├── references/ ← docs sob demanda
│ ├── caso-a.md
│ └── caso-b.md
├── scripts/ ← código reutilizável
│ └── validate.py
└── assets/ ← templates, fontes
└── template.md

Os 3 níveis de carregamento

Nível 1 Metadados
Só name + description. Sempre no contexto. Custo fixo de ~30–100 tokens por skill por prompt.
Nível 2 Corpo do SKILL.md
Carregado só quando a skill dispara. Mantenha abaixo de 500 linhas / 5.000 tokens. Detalhes vão para references/.
Nível 3 Recursos externos
Scripts rodam sem ser lidos. References entram no contexto apenas quando o SKILL.md instrui explicitamente.

Exemplo completo — SKILL.md

ga4-tagging/SKILL.md Nível 1 + 2 
---
name: ga4-tagging
description: Use para tudo relacionado a tagueamento GA4 — estrutura
  de dataLayer, eventos personalizados, GTM e tracking plan.
  Use sempre que o usuário mencionar GA4, GTM, dataLayer,
  analytics, tracking ou tagueamento, mesmo sem citar "skill".
---

# GA4 Tagging

## Quando usar cada referência
- Padrões de dataLayer → leia references/data-layer.md
- Schema de eventos     → leia references/event-schema.md
- Nomear eventos        → leia references/naming.md
- Validar antes entregar→ rode scripts/validate.py

## Fluxo: Criação de Eventos
1. Receber contexto (qual ação rastrear)
2. Verificar se é evento recomendado ou customizado
3. Nomear corretamente (snake_case, máx 40 chars)
4. Gerar código + documentar no tracking plan
5. Validar com scripts/validate.py

## Gotchas
- Eventos customizados: padrão objeto_acao (ex: menu_click)
- Parâmetros: máx 100 chars de valor string
- Nunca usar camelCase — GA4 é case-sensitive
02

Description — o gatilho

A description é a parte mais crítica de qualquer skill. O Claude decide se usa a skill baseado apenas no name + description. Ela carrega 100% da responsabilidade de acionamento — tudo que não está aqui é invisível para o sistema de seleção.
❌ Fraca
description: Cria relatórios financeiros.

Sem contexto de quando usar. Sem palavras-chave. Nunca vai disparar em prompts reais.

✓ Forte
description: >
  Cria relatórios financeiros. Use sempre
  que o usuário mencionar margens, receita,
  planilhas de custo, dashboards de vendas
  ou quiser visualizar dados de performance
  — mesmo sem pedir explicitamente um
  "relatório".
01 Use imperativo

Escreva "Use esta skill quando…" em vez de "Esta skill faz…". O Claude está decidindo se deve agir — diga a ele quando agir.

02 Foque na intenção

Descreva o que o usuário quer alcançar, não os detalhes internos da skill. O Claude faz matching pela intenção do prompt.

03 Seja "agressivo"

Liste contextos onde a skill se aplica, incluindo casos onde o usuário não cita o domínio diretamente. O Claude subtrigger por padrão.

Limite Máximo 1024 caracteres

A especificação oficial impõe um limite rígido de 1024 chars na description. Descriptions crescem durante a otimização — monitore o tamanho. Conciso e específico supera longo e genérico.

03

Gerenciando Tokens

Custo fixo por número de skills

5–10 skills
~500–1k
20–30 skills
~2k–4k
50+ skills
~5k–10k
Contexto total
200k

10 skills bem escritas = menos de 0,5% do contexto disponível. O gargalo real é qualidade, não quantidade.

Como economizar tokens

  • ✓ Descriptions curtas e precisas2–4 frases. Cada palavra extra é custo fixo em todo prompt.
  • ✓ Mover detalhes para references/Tudo raramente necessário sai do SKILL.md e carrega sob demanda.
  • ✓ Scripts que rodam sem ser lidosCódigo em scripts/ é executado sem entrar no contexto — zero tokens.
  • ✓ Consolidar skills redundantesDuas skills parecidas = dobro do custo fixo + ambiguidade no gatilho.
  • ✓ Adicionar só o que o agente não sabeNão explique HTTP, PDFs, ou conceitos básicos. O agente já sabe. Foque no específico do seu domínio.

Boas Práticas de Escrita

✓ Faça

Explique o porquê das instruções, não só o quê
Use imperativo: "Identifique", "Gere", "Valide"
Inclua exemplos concretos Input → Output
Dê um default claro quando há opções
Adicione seção de Gotchas com pegadinhas específicas
Instrua quando ler cada reference explicitamente

✗ Evite

Usar SEMPRE/NUNCA em caps sem explicação
Instruções ultra-específicas que só funcionam para 1 caso
Menus de opções sem default: "use pypdf, pdfplumber ou PyMuPDF…"
Explicar o óbvio que o agente já sabe
SKILL.md com mais de 500 linhas
Só testar 1 prompt e assumir que funciona
Explique o porquê
❌ SEMPRE inicie pelo sumário.

✓ Inicie pelo sumário porque o usuário
  geralmente lê só a primeira página —
  ela precisa ser autoexplicativa.
Default, não menu
❌ Use pypdf, pdfplumber ou PyMuPDF...

✓ Use pdfplumber para extração de texto.
  Para PDFs escaneados, use pdf2image
  com pytesseract como fallback.
Procedimento vs declaração
❌ Faça JOIN de orders em customers.

✓ 1. Leia o schema de references/
  2. Use a convenção _id para joins
  3. Aplique filtros como WHERE
  4. Formate como tabela markdown
05

References — documentação sob demanda

References são arquivos de apoio que o Claude lê somente quando necessário. Mantêm o SKILL.md enxuto e os tokens sob controle.

Quando criar um reference

  • →Documentação técnica detalhada (APIs, schemas, padrões)
  • →Conteúdo necessário apenas em cenários específicos
  • →Múltiplos domínios/frameworks (aws.md, gcp.md, azure.md)
  • →Quando o SKILL.md está se aproximando de 500 linhas

Como referenciar corretamente

## Quando usar cada reference

# ✓ Específico — o Claude sabe quando carregar
- Se a API retornar erro não-200 →
  leia references/api-errors.md
- Para nomear eventos →
  leia references/naming.md

# ✗ Genérico — inútil
- Veja references/ para detalhes.
ga4-tagging/references/event-schema.md Nível 3 
# Schema de Eventos GA4

## Índice
1. Eventos recomendados pelo Google
2. Eventos customizados
3. Parâmetros globais obrigatórios

## 1. Eventos recomendados (use sempre que possível)
| Evento        | Quando usar          | Parâmetros obrigatórios         |
|---------------|----------------------|---------------------------------|
| purchase      | Finalização compra   | transaction_id, value, currency |
| add_to_cart   | Adicionar carrinho   | item_id, item_name, value       |
| login         | Login usuário        | method                          |

## 2. Eventos customizados
Use quando não há equivalente recomendado.
Padrão: {objeto}_{acao} → banner_click, form_submit, video_play

## 3. Parâmetros globais (incluir em todos)
- event_category  → agrupamento lógico
- page_location   → URL atual
- user_logged_in  → boolean
References com mais de 300 linhas precisam de um índice no topo para o Claude saber onde procurar sem ler tudo.
06

Scripts — código reutilizável

Quando criar um script

Se em vários testes o Claude escreve o mesmo helper script independentemente, esse código deve ir para scripts/. Escreva uma vez, use em todas as execuções — economiza tokens e tempo.

Scripts rodam sem ser lidos

O agente executa scripts com um comando — sem carregar o código no contexto. Dependências declaradas inline com uv run são instaladas automaticamente.

4 regras de ouro para scripts agenticos

⚠ Sem prompts interativos
# Agentes não podem responder prompts
# ✗ RUIM: trava indefinidamente
Target environment: _

# ✓ BOM: erro claro com orientação
Error: --env é obrigatório.
Opções: development, staging, production
Usage: python deploy.py --env staging
📋 --help bem documentado
# --help é como o agente aprende
# a interface do seu script
Usage: validate.py [OPTIONS] INPUT

Options:
  --format FORMAT  json, csv, table
  --output FILE    salvar em arquivo
  --verbose        log no stderr

Examples:
  validate.py data.csv
  validate.py --format csv out.csv
📊 Output estruturado
# ✗ Difícil de parsear
NAME       STATUS   CREATED
my-service running  2025-01

# ✓ JSON — consumível pelo agente
{"name": "my-service",
 "status": "running",
 "created": "2025-01-15"}

# Dados → stdout
# Diagnósticos → stderr
🔁 Idempotente + --dry-run
# Agentes podem repetir comandos
# "crie se não existir" > "crie e falhe"

# Para operações destrutivas:
python deploy.py --dry-run
# Mostra o que vai acontecer
# sem executar de fato

# Exit codes distintos por tipo de erro:
# 1=not found, 2=invalid args, 3=auth

Exemplo: script com dependências inline (PEP 723)

ga4-tagging/scripts/validate_events.py uv run scripts/validate_events.py events.json 
# /// script
# dependencies = [
#   "jsonschema>=4.0",
#   "rich>=13.0",
# ]
# ///

import json, sys
from jsonschema import validate

# Sem prompts interativos — tudo via args
if len(sys.argv) < 2:
    print("Error: arquivo JSON obrigatório", file=sys.stderr)
    print("Usage: validate_events.py events.json", file=sys.stderr)
    sys.exit(2)

with open(sys.argv[1]) as f:
    events = json.load(f)

errors = []
for ev in events:
    if "event" not in ev:
        errors.append({"event": ev, "error": "campo 'event' obrigatório"})
    elif len(ev["event"]) > 40:
        errors.append({"event": ev["event"], "error": "nome > 40 chars"})

# Dados estruturados → stdout
print(json.dumps({"valid": len(errors) == 0, "errors": errors}, indent=2))
sys.exit(0 if not errors else 1)
Cuidado com output grande: muitos harnesses truncam automaticamente output além de 10–30K caracteres. Se seu script pode produzir output grande, suporte flags como --offset ou --output arquivo.json para que o agente possa controlar o tamanho.

Assets — templates e recursos

Assets são arquivos usados na produção do output final — templates de documentos, fontes, ícones, planilhas base. Diferente de references (para o Claude ler) e scripts (para executar), assets são inputs para o trabalho.

📄 Templates de output

Estruturas fixas que o output deve seguir. Armazene em assets/ e instrua o Claude a usá-las como base. Mais confiável que descrever o formato em prosa.

🎨 Recursos visuais

Fontes, ícones, logos, paletas de cores. Especialmente úteis para skills de geração de apresentações ou documentos com identidade visual.

📊 Planilhas e schemas

Arquivos CSV, JSON ou YAML que servem como fonte da verdade para validações ou como estrutura base para output.

Avaliando sua Skill

Sempre compare with skill vs. without skill. Uma skill que melhora o pass rate em 50pp mas triplica tokens é um trade-off diferente de uma que é igualmente melhor e mais barata. O benchmark.json revela esse custo-benefício real.

Estrutura de workspace

minha-skill-workspace/
└── iteration-1/
├── eval-caso-a/
│ ├── with_skill/
│ │ ├── outputs/
│ │ ├── timing.json ← tokens + ms
│ │ └── grading.json ← assertions
│ └── without_skill/
│ └── outputs/
└── benchmark.json ← delta final

Boas assertions vs ruins

✓ Boas assertions

"O arquivo de saída é JSON válido"
"O gráfico tem eixos com rótulo"
"O relatório tem pelo menos 3 recomendações"

✗ Ruins

"O output é bom" — vago demais
"Usa exatamente a frase X" — frágil demais
Assertions que sempre passam nos dois lados — inúteis

O que o benchmark.json revela

{
  "run_summary": {
    "with_skill":    { "pass_rate": { "mean": 0.83 }, "tokens": { "mean": 3800 } },
    "without_skill": { "pass_rate": { "mean": 0.33 }, "tokens": { "mean": 2100 } },
    "delta": {
      "pass_rate": +0.50,   // ← skill melhorou 50pp = vale a pena
      "tokens":    +1700    // ← custo de 1700 tokens extras por run
    }
  }
}

Erros Comuns — Gotchas

  • ⚠
    Description vaga sem palavras-chave de contexto Sem keywords específicas, o Claude não sabe quando usar a skill. O sistema tende a undertrigger — a description precisa ser explicitamente "agressiva".
  • ⚠
    SKILL.md com 1000+ linhas Todo o corpo entra no contexto a cada uso. Conteúdo que deveria estar em references/ vira custo fixo desnecessário em todo prompt.
  • ⚠
    Usar SEMPRE/NUNCA em caps sem explicar o porquê Yellow flag. O Claude segue melhor raciocínio do que ordens brutas. Reescreva explicando a lógica por trás da restrição.
  • ⚠
    Skill criada sem contexto de domínio real Pedir ao LLM para gerar uma skill sem material específico resulta em procedimentos genéricos. Alimente runbooks, specs de API, logs de bugs resolvidos, histórico de code review.
  • ⚠
    Overfitting para os casos de teste Skill que só funciona para os 3 prompts testados. Pense em como vai se comportar em 1000 prompts diferentes. Evite patches narrow — generalize.
  • ⚠
    Scripts que bloqueiam aguardando input Agentes operam em shells não-interativos. Um script com prompt de confirmação vai travar indefinidamente. Aceite tudo via flags, variáveis de ambiente ou stdin.
  • ⚠
    Duas skills com descriptions sobrepostas Quando ambas poderiam disparar para o mesmo prompt, cria ambiguidade no acionamento. Delimite claramente o território de cada uma com exemplos de quando NÃO usar.
  • ⚠
    Não versionar com iterações separadas Ao melhorar uma skill, nunca edite o original diretamente antes de ter o baseline salvo. Snapshote a versão anterior para poder comparar o delta real.
  • ⚠
    Scripts com output de texto livre grande Harnesses truncam output acima de ~10–30K chars silenciosamente. Scripts que podem gerar muito texto precisam suportar --output arquivo ou --offset para paginação.
10

Loop de Iteração

O loop é o coração do processo. Uma skill boa não é escrita de uma vez — ela é refinada através de execuções reais, avaliação honesta e melhorias focadas.

1
Rascunho inicial
Escreva o SKILL.md. Antes, complete a tarefa real com o Claude e extraia o padrão. Ou alimente material interno: runbooks, specs de API, code reviews, bugs resolvidos.
2
Crie 2–3 casos de teste realistas
Prompts que um usuário real digitaria. Varie formalidade, detalhe, e explicitness. Inclua pelo menos um edge case. Salve em evals/evals.json.
3
Rode: with skill + without skill
Execute cada caso duas vezes — uma com a skill, uma sem. Contextos limpos e separados. O resultado sem skill é o baseline de comparação.
4
Avalie os outputs
Leia os execution traces, não só os resultados finais. Se o agente desperdiçou tempo em passos improdutivos, as instruções estão ambíguas ou excessivas. Grade assertions, colete feedback humano.
5
Melhore — generalize, não patcheie
Corrija o problema subjacente, não o sintoma específico. Se as correções são muito narrow (só funcionam para aquele exemplo), você está overfitting. Adicione gotchas para erros recorrentes. Remova instruções sem pull.
6
Repita em iteration-N+1/
Salve os resultados da nova iteração em um diretório separado. Compare com a iteração anterior. Pare quando o feedback for consistentemente vazio ou o progresso for marginal.
7
Otimize a description
Crie ~20 queries de eval (10 should-trigger, 10 should-not-trigger). Teste com train/validation split (60/40). Itere a description com base nos failures do train set — valide no held-out. Limite: 1024 chars.
🏁 Critérios de parada
✓
Feedback consistentemente vazio — tudo está bom
📊
Delta de pass rate entre iterações abaixo de 5pp
💬
Você está satisfeito com os outputs em casos reais
